# Development roadmap

This roadmap keeps the next work in dependency order. Prefer small changes with a focused unit test or integration check. Revisit the order when implementation reveals a real dependency; do not rewrite the CPU just to make the design look cleaner.

## Development priorities

- Make emulation correctness the first priority. Define hardware behavior from reliable specifications and observable behavior, and cover it with focused unit or integration tests.
- Once behavior is tested and stable, measure performance before optimizing. Implementation and storage choices must not define emulation behavior or rely on operating-system-specific semantics in the core.
- Keep platform-specific file access behind a narrow boundary so the emulator core can use portable ROM storage and support alternate backends when profiling justifies them.

## Completed foundation

- CPU instruction execution advances in M-cycle steps.
- Decoder metadata is compiled into typed C++ tables from the CSV source files.
- CPU interface and instruction unit tests run through `make test`.
- GitHub Actions builds the project, runs unit tests, and checks instructions against a pinned GBIT fork.
- Regression coverage includes DAA, `ADD SP,e8` flags, EI delay, stack/jump memory-cycle sequences, and the M-cycle when PUSH/POP update SP.
- Polymorphic interfaces used through owning pointers now have virtual destructors. `GBCPU` marks memory/decoder dependencies as borrowed references, and each GBIT adapter owns its dependencies and helper independently.
- A regression test creates two GBIT adapters, destroys one, and verifies that the other remains usable.
- CPU-local STOP and HALT states are separate; STOP consumes its second byte, ignores its value, and resumes fetching only after an explicit wake request.
- The CPU stepping interface defines one M-cycle as four T-cycles and reports elapsed T-cycles per step (zero during STOP idle). Tests check elapsed time and memory accesses across instruction M-cycles.
- The initial DMG PPU owns VRAM/OAM and implements LCD registers, 456-dot scanlines, mode 0/1/2/3 transitions, VBlank and edge-triggered STAT requests, mode-based CPU video-memory access restrictions, and a headless 160×144 DMG shade-index framebuffer. Its scanline renderer draws the background, window, and 8×8/8×16 objects with tile addressing, palettes, transparency, and DMG object priority. Mode 3 still uses its 172-dot minimum, and the renderer samples state once at the end of mode 3, so mid-scanline register changes and their timing effects are not modeled yet.
- FF46 OAM DMA copies 160 bytes from the selected address page into PPU OAM. The transfer is currently immediate; CPU blocking and per-byte DMA timing are not modeled.
- `GameBoySystem` starts from a no-boot-ROM DMG post-boot profile for the implemented CPU, timer, joypad, interrupt, APU, and PPU state. System tests request the synthetic CPU-reset state through the explicitly named `GameBoySystem::createForTest()` factory. `stepFrame()` advances one nominal 70,224-T-cycle frame and reports an incomplete frame if STOP freezes CPU/system time.
- The initial DMG APU is clocked with the system: pulse channels 1 and 2, wave channel 3, noise channel 4, channel 1 sweep, length/envelope clocks, stereo routing, 48 kHz PCM generation, and libretro audio callback delivery. The frame sequencer now clocks from falling edges of divider bit 12, including a DIV write that resets the bit while high. CPU bus transactions are scheduled after three T-cycles of each M-cycle. This lets DMG wave RAM reads and writes occur on CH3's sample-fetch T-cycle; Blargg test 09 passes in the ROM-only DMG core, while tests 10 and 12 remain to be checked.

## Delivery milestones

The first playable milestone is running a Game Boy ROM in RetroArch on Ubuntu. Build and test the shared headless core first; it is a prerequisite, not a separate player-facing milestone. Do not make a standalone GUI a prerequisite.

1. **First playable milestone: Ubuntu RetroArch core.** Implement the shared clock and bus, address map and initial cartridge loading, timer and interrupts, then a minimal PPU, input path, and libretro adapter. Acceptance: build a Linux libretro shared library; RetroArch loads a supported homebrew ROM; the game produces video frames and responds to input through a short gameplay loop. Use [GB Pong Clone](https://github.com/AlexMGiroux/gb-pong-clone), now confirmed as a 32 KiB ROM-only cartridge under MIT, as the acceptance game. RetroArch 1.7.3 loaded the core and ran Pong for 60 frames under Xvfb; the in-process libretro test verifies that Up visibly changes the Pong frame. Interactive controller verification remains the final check. Audio and save persistence are not required for this milestone.
2. **Audio and compatibility — in progress.** The APU produces stereo PCM for all four DMG channels and sends it through libretro. Refine APU timing and register behavior, add cartridge persistence, then improve timing and visual compatibility with focused tests and reference games. Use Game Boy F-1 Race as one PPU visual target.
3. **Steam Deck.** Build and verify the libretro core in RetroArch on SteamOS, including controls, display scaling, and audio.
4. **Raspberry Pi with Recalbox.** Build and verify the core for the supported Raspberry Pi model and Recalbox environment, including controls, video, and audio.
5. **Windows.** Add a Windows build and CI job for the libretro core, then verify it in a Windows RetroArch installation.

## Next work, in order

1. **Integrate the shared system clock and bus — initial T-cycle bus phase implemented.** Keep CPU stepping at one M-cycle (four T-cycles), and make the system scheduler the time authority for CPU and peripherals. The scheduler advances devices by three T-cycles before the CPU bus transaction and by the remaining one afterward; steps without a transaction advance devices after the CPU step. Reset's initial opcode fetch now occurs in the first timed CPU step. This finer phase was added because Blargg's CH3 wave RAM read test exposed that M-cycle-only access handling always returned `$FF`; test 09 now passes, and the phase should be checked against any PPU and timer ROMs added later.
2. **Add a real address bus and cartridge boundary.** Address-range routing, zero-initialized VRAM/WRAM/OAM/HRAM regions, and a ROM-only cartridge window are composed into an initial headless system and covered by tests. ROM-only cartridges are limited to at most 32 KiB; full header parsing, file loading, banked mappers, echo RAM, and hardware-backed I/O devices remain to be implemented. Keep the GBIT memory adapter as test infrastructure.
3. **Add timer and interrupt components.** The initial DMG timer registers (`DIV`, `TIMA`, `TMA`, `TAC`), divider-edge counter, delayed overflow reload, and timer interrupt request/enable registers are mapped and covered by focused tests. The CPU now accepts enabled requests at instruction boundaries, applies priority, acknowledges only the selected IF bit, pushes the return PC and vectors through a five-M-cycle interrupt-entry sequence, and handles IME delay, HALT wake-up, and the HALT bug. Timer and CPU depend on an interrupt-controller interface so other hardware sources can request interrupts without depending on the IF/IE register implementation. Further refine timer/interrupt edge timing against dedicated ROM tests as those suites are added.
4. **Add the PPU and input path.** The JOYP register is mapped at `FF00`, with active-low direction/button selection, falling-edge interrupt requests, and a `GameBoySystem` button-state API covered by unit and system tests. The initial DMG PPU now owns VRAM/OAM, LCD registers, line/mode timing, VBlank/STAT requests, mode-based CPU access restrictions, and scanline rendering for background, window, and objects. FF46 DMA transfers object data into OAM, without modeling its CPU stall timing yet. The headless frame buffer is exposed by `GameBoySystem` for a future frontend. An automated dmg-acid2 visual regression compares the frame buffer with the upstream reference. This ROM does not test mode 3 timing penalties. Keep rendering/UI separate from emulation state. Use Game Boy F-1 Race as a later visual compatibility target.
5. **Define cartridge startup and frame stepping — implemented.** Normal `GameBoySystem` construction starts at `$0100` with the documented DMG CPU register values, initializes the implemented timer/interrupt/joypad/APU/PPU state, and skips the boot-ROM animation. System tests use the explicitly named `GameBoySystem::createForTest()` factory for the synthetic CPU-reset state; `GBCPU::reset()` remains unchanged. `stepFrame()` advances 70,224 T-cycles and returns elapsed time; it exits with `frameCompleted == false` if STOP prevents further clock progress. Boot-ROM execution and model-specific power-on variation remain outside this initial DMG profile.
6. **Libretro adapter — implemented; interactive input check remains.** `make build` produces `build/lotusgb_libretro.so`; it loads in-memory ROM-only content, advances one frame per `retro_run()`, forwards joypad buttons, and publishes the 160×144 DMG framebuffer. GBIT-only source files are excluded from this core build. In-process frontend tests check API metadata, video callbacks, exact dmg-acid2 output, visible Pong input response, and channel 1 PCM delivery. Ubuntu RetroArch 1.7.3 successfully loaded the core and ran Pong for 60 frames under Xvfb. Before declaring the first playable milestone complete, verify the mapped controls in an interactive RetroArch session. Keep RetroArch-specific lifecycle and callbacks outside CPU and hardware components.
7. **Refine DMG audio and add cartridge persistence.** All four DMG channels currently produce stereo PCM through the libretro batch callback and have component/frontend coverage. The frame sequencer is driven by the timer's divider-bit-12 falling edge, including DIV reset writes; focused Timer, APU, and system tests cover that wiring and channel-length clocking. CH3 now waits three extra 2 MHz APU ticks before its first sample fetch after a trigger, and DMG wave RAM access is allowed only on the same T-cycle as a sample fetch. Focused APU tests cover the startup delay and fetch-cycle alias, and Blargg's `09-wave read while on` ROM now displays `Passed` in the ROM-only DMG core. Next use tests 10 and 12 to check triggering and writes. Our ROM-only cartridge does not expose external RAM, so the suite's `$A000` result protocol cannot yet be used by an automated runner; use its on-screen result until cartridge RAM support is added. For CH4, the [Game Boy Noise Test](https://github.com/not-chciken/gb-noise-test) provides interactive NR41–NR44 settings, game-inspired presets, and reference recordings made from a DMG-01. Use it for listening or captured-PCM comparison, since the DMG does not expose channel samples to the CPU for a ROM pass/fail check. SameSuite's APU tests are sample-accurate, but most depend on CGB-only PCM registers and are not a DMG acceptance target. Then add cartridge header parsing, a mapper with battery-backed RAM, and save/load through libretro's memory interface; persistence depends on the cartridge boundary and mapper support.

## Code cleanup

- **Synthetic test startup separation — implemented.** Normal system construction always uses the DMG post-boot profile. Tests request the synthetic CPU-reset profile through `GameBoySystem::createForTest()`, so `TestReset` is no longer a normal startup-mode option.

## Open design questions

These are discussion prompts, not approved implementation tasks. Discuss them one at a time; promote an item into the roadmap only if it is worth addressing.

1. **Clock and bus timing for the PPU.** CPU bus transactions currently occur after three T-cycles of a four-T-cycle M-cycle. Is that phase sufficient for PPU mode transitions and VRAM/OAM access restrictions, or do targeted visual tests require moving individual bus transactions to other T-cycles?
2. **Joypad and STOP wake-up.** Should button input wake STOP in the current system, and what exact joypad signal should trigger it? The current input API updates JOYP and requests its interrupt but does not wake the CPU from STOP.
3. **CPU reference tests.** How should CI present known GBIT disagreements (currently STOP and EI) while keeping hardware behavior as the source of truth? Consider adding focused community test ROMs as their required hardware becomes available.
4. **GBIT adapter boundary.** GBIT-only sources remain in `src/lib`, but the libretro core excludes them from its build. Consider moving them into test support during later source cleanup; the main shared library still includes every `.cpp` in `src/lib`.

## Resolved design questions

- Keep virtual interfaces where they let unit tests substitute fake dependencies; do not add them to every class by default.
- Let the PPU own VRAM/OAM and route CPU access through the PPU so it can enforce mode-based access restrictions.
- For the first RetroArch core, skip boot-ROM execution and start ROM-only DMG cartridges from an explicit post-boot profile; keep CPU unit-test reset independent. Revisit boot-ROM support only if a later compatibility target needs its animation or exact handoff timing.
- Defer a broad `src` directory reorganization. Isolate GBIT adapter code before libretro, then group hardware modules when the PPU makes the current flat library directory harder to navigate.
- Use Pan Docs as a hardware reference and list it in the README; verify behavior with focused tests rather than treating any one reference emulator as the specification.

## Validation rule

For each step, state what externally observable behavior changes, add a focused regression test at the narrowest useful boundary, and run the relevant unit or integration checks. Use GBIT as one CPU comparison source; investigate disagreements instead of copying behavior without hardware evidence.

## Test ROMs and acceptance

- Use focused tests from the [Mooneye Test Suite](https://github.com/Gekkio/mooneye-test-suite) and [Blargg test ROM collection](https://github.com/c-sp/game-boy-test-roms) for CPU, timer, interrupt, memory, and other hardware behavior as those features become available. Record each selected ROM's model, boot ROM, hardware dependencies, and pass/fail signal. Do not make passing an entire suite an early milestone.
- **APU ROM targets:** Blargg's [DMG sound suite](https://github.com/retrio/gb-test-roms/tree/master/dmg_sound) covers CPU-visible APU behavior; `09-wave read while on`, `10-wave trigger while on`, and `12-wave write while on` target CH3 wave RAM behavior. The [Game Boy Noise Test](https://github.com/not-chciken/gb-noise-test) is an interactive CH4 listening tool with DMG-01 reference recordings, not an automated pass/fail test. Do not check in Blargg binaries until their redistribution terms are clear. The Noise Test project is Apache-2.0 licensed; if we vendor its ROM, include the required license notices and pin its checksum.
- **DMG PPU visual acceptance passed (2026-10-21):** [dmg-acid2 v1.0](https://github.com/mattcurrie/dmg-acid2/releases/tag/v1.0), 32 KiB ROM-only, DMG mode, no actual boot ROM. A temporary runner compared a 60-frame output with the published `reference-dmg.png`: all 23,040 pixels matched. The checked-in regression now starts from the DMG post-boot profile, runs the ROM for 10 frames from `$0100`, and compares the 160×144 shade-index framebuffer exactly. ROM SHA-256: `464e14b7d42e7feea0b7ede42be7071dc88913f75b9ffa444299424b63d1dff1`. ROM, reference image, and MIT attribution are in `tests/roms/dmg-acid2/`. The test uses LY=LYC interrupts to change settings between scanlines and does not test mode 3 penalties or mid-mode-3 writes.
- **Gameplay input regression:** [GB Pong Clone](https://github.com/AlexMGiroux/gb-pong-clone), 32 KiB, cartridge type `$00` (ROM-only), distributed under MIT. The libretro test runs 60 frames with neutral input and 60 with Up held; the resulting framebuffers differ. ROM SHA-256: `9c5e337db0ee1416f2c7f1de02e7e0a78a6064cf1da49209b4bc1a36a7b35415`. ROM and license attribution are in `tests/roms/gb-pong/`.
- Use a supported, legally distributable homebrew game for the first playable RetroArch acceptance check. The current candidate is GB Pong Clone; confirm its mapper and ROM redistribution terms before treating it as the fixed target. The check must include an input that visibly changes gameplay, not only a loaded core or static frame.
- Keep downloaded ROM binaries out of the repository unless their redistribution terms are clear. Pin the selected source or release and record a checksum for repeatable local and CI runs.

## Platform support

Use Linux as the primary development and CI platform for now. Steam Deck, Raspberry Pi running Recalbox, and Windows are target platforms. Build the portable emulator core and libretro adapter first, then add platform-specific build and integration checks. Keep code and build configuration portable where practical; defer dedicated checks for each target until the core and libretro adapter are established.
