# 神奇寶貝綠寶石 RFU 協定細節

[繁中設計說明](gba-rfu-protocol.zh-TW.md) · [English overview](gba-rfu-protocol.md) · [English details](gba-rfu-protocol-details.md) · [術語表](gba-link-glossary.zh-TW.md)

本文件補充 RFU 命令格式、遊戲資料傳送層和 LotusGBA 的同步策略。若只想了解目前支援範圍與模擬取捨，請先看[繁中設計說明](gba-rfu-protocol.zh-TW.md)。

## 適用範圍與來源

協定依據英文版《神奇寶貝綠寶石》的 RFU 程式，主要參考 `librfu.h`、`librfu_stwi.c`、`librfu_intr.c`、`librfu_rfu.c`、`AgbRfu_LinkManager.c` 和 `link_rfu_2.c`。LotusGBA 的連線設定檔可辨識英文版 `BPEE` 和日文版 `BPEJ`；日文版實際遊戲連線尚未驗證。

這裡記錄的是遊戲程式使用的介面和核心實作契約，不是完整的 RFU 硬體規格。合成 NI 身分測試不是商業遊戲或真實 RFU 硬體測試。

## STWI 與 SIO 命令

綠寶石透過 SIO 序列介面傳送 STWI 命令。命令使用 32 位元資料字；標頭帶命令編號和後續資料字數。一般成功回覆會在命令編號加 `0x80`，並帶回覆資料字數；拒絕命令使用 `0x996601EE` 和錯誤碼。

GBA 平常提供 SIO 時脈。`0x25`、`0x27` 等命令的成功回覆可把時脈控制暫交給 RFU 轉接器，讓轉接器送出下一個事件或命令；遊戲回覆後再交回 GBA。這個 SIO 時脈切換和 RFU 主端／子端角色不同。

| 命令 | 用途 | LotusGBA 行為摘要 |
|---|---|---|
| `0x10`–`0x17` | 初始化、狀態查詢、遊戲與系統設定 | 回覆或保存連線設定檔所需資料；沒有完整模擬 RFU 身分和所有檢查碼行為。 |
| `0x19`–`0x21` | 搜尋主端／子端並嘗試連線 | 對應到 Netplay 廣告和雙端連線狀態；不模擬多個子端插槽分配。 |
| `0x24`、`0x25` | 傳送 RFU 資料；`0x25` 另切換 SIO 時脈 | 保存待送資料，依同步策略完成本機回覆與網路傳送。 |
| `0x26` | 讀取已收到的 RFU 資料 | 回傳已完成接收的 LLSF 資料；網路額度不代表遊戲已讀取。 |
| `0x27`–`0x29` | 切換時脈、資料就緒與斷線事件 | 依傳輸狀態產生事件；`0x28` 通常由遊戲以 `0xA8` 回覆。 |
| `0x30`、`0x3D` | 中斷連線或停止搜尋 | 清除本機連線狀態，或結束搜尋但保留區域網路上的 Netplay 連線。 |
| 其他命令 | 測試、復原或未確認用途 | 未實作的命令預設拒絕；這不代表所有遊戲流程都不會需要它們。 |

成功的 RFU 搜尋還不等於遊戲玩家已加入。遊戲會繼續交換遊戲名稱、序號等資料，之後才接受身分和應用層訊息。

## NI、UNI 與 LLSF

綠寶石 RFU 程式把應用資料分成 NI（Numbered Information，編號資訊）和 UNI（Un-Numbered Information，非編號資訊）。NI 會分階段傳送資料，並追蹤階段序號和確認狀態；UNI 使用另一套接收狀態，包含新資料旗標與資料覆寫錯誤。兩種資料都封裝在 LLSF（Link Layer Subframe，連結層子影格）中。

`0x24`／`0x25` 的傳輸外框帶有 LLSF。主端和子端的標頭長度不同：主端 LLSF 標頭為 3 位元組，子端為 2 位元組。標頭包含資料類型、插槽、階段、序號／確認狀態及負載長度。`0x26` 回覆中的接收 metadata 是 STWI ACK 後的一個資料字，不是重複的 LLSF 標頭。

NI 內部的重送與確認狀態由遊戲 RFU 程式管理。LotusGBA 不把網路傳輸層的序號或額度確認當成 NI 確認；UNI 也不能只因負載位元組相同就一律去重。

## Ghost Send（幽靈傳送／空載輪詢傳輸）

綠寶石的 RFU 主端在沒有新應用資料時，仍可能以一個位元組發起 RFU 交換，讓子端回傳已排程的資料。這種 Ghost Send 不是零位元組應用封包。來源程式在 `rfu_REQ_sendData` 中設定一個位元組的傳送長度；轉接器會使用保留的 TX 前綴完成交換。LotusGBA 以有明確初始化的緩衝區處理此情境；硬體上電時 TX 記憶體內容沒有驗證。

## LotusGBA 的同步策略

RFU 主端在實際介面中發起無線交換；子端將資料排入轉接器，等待主端交換。LotusGBA 保留不同同步策略作為參考與實驗：

| 策略 | 行為 | 重要差異 |
|---|---|---|
| `RemoteReply` | 等待真正的網路對等端回覆。 | 最接近保守的逐次往返參考行為。 |
| `GuardedLocalPoll` | 主端可在等待期間重複完成本機輪詢，但身分和資料區塊仍等待真實對等端。 | 不預測對等端資料，也不產生 NI ACK；以來源推導的遊戲關卡限制本機輪詢。 |
| `GroupedCommands` | 將符合條件的命令分組，使用有界緩衝減少逐命令等待。 | 分組前段的本機完成不代表遠端收到；最後一段仍以真實回覆作為 fence。 |
| `AsyncAdapter` | 兩個方向成為各自排序的 Netplay 資料流。 | 本機傳輸接收資料後可先完成本機命令；不代表遠端收到或遊戲完成。佇列滿時採背壓。 |

目前玩家可見的 LAN 交換是在 AsyncAdapter 路徑上觀察到；不同策略的單元測試結果不能當成同一個遊戲驗收結果。

## ACK、網路額度與遊戲確認不是同一件事

LotusGBA 以 RetroArch Netpacket 的可靠模式送出封包；前端負責可靠、有序地傳送。核心不自行重做 TCP 的丟包重送。下表的「接收額度」是另一層用途：它限制對方核心尚未交給遊戲處理的資料量。

| 層級 | 完成表示 | 不表示 |
|---|---|---|
| STWI ACK | 本機 RFU 介面接受命令 | 網路對等端收到資料 |
| Netplay 接收額度 | 對端核心把資料放入有界佇列 | ROM 已讀取 `0x26` 或解析 NI／UNI |
| RFU 事件／`0xA8` | RFU 事件和 SIO 時脈交接完成 | NI 傳送或遊戲加入完成 |
| LLSF 內的 NI ACK | 遊戲 RFU 程式確認指定階段／序號 | 後續交換或交易完成 |

這些界線可避免核心把「封包已排隊」誤當成「寶可夢已成功交換」。身分、交換資料、完成確認和取消仍由遊戲程式處理。

## 測試能涵蓋的範圍

合成兩系統測試使用原創 loop ROM 和獨立 NI 測試程式，透過公開 SIO 暫存器及 CPU 執行交換資料。涵蓋項目包括：

- NI 身分、階段序號、ACK、結束標記和錯誤序號拒絕。
- 零延遲、雙向延遲、不對稱延遲、抖動與延遲網路額度。
- 本機輪詢、回覆競態、斷線取消和有界逾時。
- RFU SIO 橋接中的時脈交接、不可變傳輸快照、子端回覆與佇列額度。

這些合成測試以 service tick（服務刻度）推進，不是按真實時間計時。延遲測試能檢查程式在指定排程下如何處理資料順序、重試和逾時，但不能換算成可支援的 RTT 門檻，也不能代表綠寶石實際使用的逾時時間。

交換、存檔重開及對戰的驗證結果請見 [RFU 設計說明](gba-rfu-protocol.zh-TW.md#目前的驗證結果)。取消後重新連線及真實轉接器的時序仍待驗證。
